后端 POC：把专业名词变成具体场景

先记住一句话：Phase 1 POC 只验证“用户授权后，broker 能不能安全地保存 refresh token、持续换新父 token，并且避免多个请求同时刷新把链弄坏”。它还没有做 agent policy、scoped child token、MCP、WebUI 或审计。

这套链条在正常情况下解决什么？

你在浏览器里显式授权一次。GitHub 给 broker 一个短期“父 token”和一个长期但不能长期存放明文的“refresh token”。父 token 过期后，broker 用 refresh token 换新的父 token和新的 refresh token。以后 agent 需要访问 GitHub 时，不需要你每次都重新授权。

它不解决什么？

它还不决定某个 agent 能访问哪个仓库，也不生成最终发给 agent 的最小权限 child token，更不防止同用户下完全恶意进程。那些属于后续 Phase 2/3 和威胁模型边界。

接受 POC 与不接受 POC 的实际差异

决策接下来会发生什么具体例子成本/风险
接受把当前 token chain 当作 Phase 2 的技术地基，后续 exec wrapper、git credential helper、policy 都建立在“父 token 内存缓存 + refresh token 加密轮换”之上。例如之后做 git credential helper 时，默认假设：broker 能返回一个仍有效的凭据，并且 refresh 冲突已经在核心层处理。如果核心语义错了，越晚推翻成本越高；接受不代表永久批准 SQLite 驱动、schema 或所有实现细节。
部分接受/要求修改保留 device flow 或加密思路，但先改你不同意的点，例如不用 SQLite、改变 CLI 表面、改变状态机或要求真实 GitHub 冒烟后再定。例如你担心 master key 在 WCM 中无法备份，那么可以先要求设计备份/恢复，再进入 Phase 2。现在修改成本最低；缺点是 Phase 2 会等待。
拒绝不把当前 POC 当作技术地基，后续实现不得假设它存在；需要重新决策 secret store 和 token chain。例如改为直接使用 Windows Credential Manager 逐条存 refresh token，就要重新解决“refresh token 与过期状态必须同事务更新”的问题。避免错误地基，但会重做 POC 和部分架构验证。

建议你审查时问的三个问题

  1. 我是否接受“refresh token 加密存 SQLite，master key 只放 Credential Manager”作为继续实现的方向？
  2. 我是否接受“普通 token 请求绝不自动弹 device flow，只有用户显式点 reauth 才重新授权”？
  3. 我是否理解并接受“最终安全性依赖单一 daemon 管理 token chain；多个独立进程同时当 owner 不是目标”？

# AGENT_RULES — 根/领域规则分层与经验晋升机制

最近更新：2026-11-27

本文定义根 `AGENTS.md`、领域规则文件和局部经验之间的分层关系。目标是让 agent 能沉淀必要经验，同时把人工审核集中在真正影响全局行为的变化上。

## 1. 分层模型

| 层级 | 位置 | 内容 | 修改授权 |
|---|---|---|---|
| L0 全局规则 | 根 `AGENTS.md` | 全局安全、秘密、Git/push、跨分支优先级、文档地图、规则地图 | 实质性新增/修改既有约束必须明确用户批准；纯机械修正可按当前任务授权 |
| L1 领域规则 | `docs/agent-rules/<domain>.md` | 某一分支/领域特有的实现约束、验证方式、经验和禁 | 在当前任务授权和 branch ownership 内由 agent 维护 |
| L2 目录规则 | 子目录 `AGENTS.md` | 仅当该目录自包含且目录边界等于规则边界时使用 | 按对应 ownership 维护；不得弱化 L0/L1 |

本项目当前优先使用 `docs/agent-rules/`，因为 WebUI/backend 的逻辑领域并不完全等于单个目录。目录内 `AGENTS.md` 只用于真正自包含的子树。

## 2. 读取规则

1. 所有任务都必须先读根 `AGENTS.md` 和 [PROJECT_STATUS](PROJECT_STATUS.md)。
2. 按当前分支或文件 ownership 读取 `docs/agent-rules/registry.json` 中登记的领域规则。
3. 只有进入对应领域/分支/路径工作时才读取该领域规则；不相关的领域规则不应增加上下文负担。
4. 当前阶段和审核门属于可变状态，不从根 `AGENTS.md` 或领域规则中复制；统一读取 PROJECT_STATUS、DECISIONS 和已批准 CR。

## 3. 经验沉淀位置

1. 一次性修复、没有复用价值的问题：写清楚 commit message 和测试即可，不强制沉淀文档。
2. 对同一领域后续任务有复用价值的经验：沉淀到对应领域规则或该领域专门文档。
3. 跨多个领域、影响全局安全/Git/发布/审核边界的经验：先以 proposal 形式提出，获得明确批准后才能提升到根 `AGENTS.md`。
4. 不确定是否属于全局约束时，先沉淀在领域层；禁止为了“保险”把局部经验直接写进根文件。

## 4. 提升到根 AGENTS.md 的条件

只有满足以下任一条件，才可提议提升为全局约束：

- 多个领域/分支都需要遵守；
- 涉及秘密、身份、push、发布、阶段审核门或其他全局高风险边界；
- 不提升会导致跨领域规则冲突；
- 属于所有 agent 必须无条件遵守的行为。

提升前必须给出：原局部约束、拟新增/修改的全局约束、影响范围和为什么领域层不足以表达。审批后才能修改根 `AGENTS.md`。

## 5. 冲突与优先级

1. 根 `AGENTS.md` 优先于领域规则和目录规则。
2. 领域规则只能更严格或更具体，不得放宽根约束。
3. 同一任务适用多个领域规则时，按 `docs/branch-ownership.json` 与 registry 中的领域归属确定；冲突不能自动选择，必须标为待确认。
4. 可变状态一律以 PROJECT_STATUS/DECISIONS/CR 为准，规则文件不复制当前阶段门。

## 6. AGENTS.md mutation 保护

1. 纯新增机械链接、错别字修复或不改变语义的整理，不属于实质 mutation。
2. 修改、删除、弱化既有根约束，或通过重排改变其含义，属于 mutation。
3. mutation 必须有明确用户批准；批准证据必须能对应到具体“原约束 → 新约束”。
4. 模糊指令不能直接作为 mutation 授权；应先展示最小差异并等待确认。
5. `python scripts/check_agents_mutation.py` 检查 `AGENTS.md` 是否存在实质删除/改写行，并要求对应 D-xxxx 决策证据。该检查是 tripwire，不能自动判断用户授权是否真实。

# .gitignore Policy — GH Token Broker

最近更新：2026-11-27

本文定义什么时候、为什么以及如何修改根 `.gitignore`。根 `.gitignore` 是实际执行文件；本文是维护原则。`AGENTS.md` 不写死具体 ignore 规则，只链接本文。

## 1. 目标

并非所有生成文件都必须忽略：如果某个生成物是明确批准的评审/发布产物，并且需要作为可审查快照进入版本控制（例如当前低保真 SVG），可以有意识地追踪它。`.gitignore` 的目标是防止以下内容进入 Git：

- 秘密材料和运行时凭据。
- 本地运行时状态、数据库、WAL/SHM、缓存和队列文件。
- 编译产物、二进制、打包产物、覆盖率和测试输出。
- 日志、临时文件、崩溃转储和本地调试输出。
- OS、编辑器和个人工具生成的机器特定文件。

`.gitignore` **不是安全边界**。它只能降低误提交概率，不能替代 secret scan、代码审查和泄露响应。

## 2. 什么时候必须修改

出现以下任一情况时，应在**同一任务或引入该工具的 commit 前/同一 commit 中**更新 `.gitignore`：

1. 引入新语言、构建工具、包管理器或测试工具，并会产生本地 cache/build output。
2. 新增编译目标、二进制输出目录、coverage/report/artifact 目录。
3. 新增运行时数据目录、数据库文件、WAL/SHM、日志、pid、socket、临时队列或本地状态文件。
4. 新增本地配置/秘密样例机制，确保真实秘密文件被忽略、示例文件仍被追踪。
5. 新增前端/设计/原型工具链，产生 `node_modules`、build、cache、coverage 或生成物。
6. 新增 OS/editor/IDE 使用约定，产生机器特定 metadata。
7. 发现已有生成物出现在 `git status` 或 `git ls-files` 中。

不应等到二进制、数据库、日志或秘密文件已经被提交后才补 `.gitignore`。如果已经提交，后续处理不是简单补规则：

- 普通生成物：停止追踪并清理索引，但历史仍存在。
- 秘密材料：按 `SECURITY.md` 泄露流程处理，先撤销/轮换，再评估历史清理。

## 3. 修改原则

1. **最小必要范围。** 优先忽略明确目录或已知扩展，不用过宽的 `*` 掩盖源文件。
2. **生成物不追踪，模板可追踪。** 例如 `.env` 忽略，`.env.example` 保留。
3. **规则按类别分组并写简短注释。** 让审查者知道规则保护什么。
4. **不忽略应该审查的源文件。** 不能因为图方便忽略源码、文档、锁文件或安全脚本。
5. **谨慎使用 negation。** `!example` 必须放在对应 ignore 规则之后，并验证实际生效。
6. **跨平台考虑。** Windows 产物如 `*.exe`、`Thumbs.db`、`Desktop.ini` 需要覆盖；未来 Unix 开发工具产物也要按需要加入。
7. **生成物规则与生成者同步变化。** 删除某个工具或输出目录时可以清理规则；扩大 ignore 不需要 CR，但削弱/删除保护秘密或生成物的规则必须说明理由。

## 4. 修改前检查清单

- 新规则是否覆盖真实生成路径？
- 是否误伤源文件、文档、锁文件或测试 fixtures？
- 是否有需要保留的 example/template？
- 是否需要同步更新 `docs/DEVELOPMENT.md` 的目录约定？
- 是否已经有文件被 Git 追踪？如有，补 `.gitignore` 不会自动停止追踪，需要明确处理 index/history。
- 秘密扫描是否仍通过？

可用诊断命令：

```powershell
git status --short --ignored
git check-ignore -v <path>
git ls-files <path>
```

这些命令用于诊断，不代表允许擅自清理用户文件或改写历史。

## 5. 文件归属

- 根 `.gitignore`：实际规则，随代码/工具链变化及时更新。
- 本文：修改原则和审查清单。
- `docs/DEVELOPMENT.md`：目录/工具链事实与相关说明。
- `AGENTS.md`：只保留原则和文档地图入口，不复制具体规则。

# CR-0003 Capability-based authorization broker 契约

- 日期：2026-11-28
- 状态：`proposed`
- 来源证据：2026-11-28 用户在高保真审核中指出，仓库管理操作不应作为公共配置，而应按 agent 单独配置；它应取代粗粒度 `Administration` 权限申请。用户进一步指出，既然项目已经引入 broker，就不应被 GitHub 原生权限模型限制，例如“只允许删除某些短期分支”这类实际需求应能通过中转封装实现。用户批准新建 CR-0003 并保留 CR-0002 直至 CR-0003 定稿。
- 影响范围：PRD、ARCHITECTURE、THREAT_MODEL、TEST_PLAN、DEVELOPMENT、WebUI 高保真、backend policy/schema/API、audit、后续 MCP/operation executor、交付通道与阶段边界。
- 当前性质：**契约草案工作区，不是冻结契约，不是后端恢复实现授权。**
- 与 CR-0002 的关系：CR-0002 暂时保留为中间草案和历史上下文；CR-0003 定稿并获批准后，CR-0002 必须被显式归档或标记为 superseded，不得长期作为过期并行规范存在。

## 1. 原因

高保真审核暴露出比 CR-0002 更根本的问题：项目授权模型不应以 GitHub 原生 permission 为中心。

1. 用户心智是“我授权 agent 能做什么”，而不是“我应该选择哪个 GitHub permission”。
2. `Administration` 这类 GitHub 粗粒度权限把创建、删除、设置、协作者管理和 branch protection mutation 混在一起，无法表达真实意图。
3. 仓库管理能力不是全局公共配置；它必须按 agent、application、resource 和约束单独授权。
4. 许多真实需求无法被 GitHub 原生权限细分，例如只允许删除 `agent/*` 短期分支、禁止删除 protected branch、只允许创建私有仓库、只允许模板化保护 main。
5. 如果 agent 已持有能绕过限制的 GitHub token，仅在 broker API 层提供细粒度 operation 不能形成真实安全边界。

## 2. 原行为/原设计

- WebUI 高保真曾以 GitHub permission matrix 为中心，并把仓库管理操作作为单独的公共 operation capability 区块展示。
- CR-0002 已识别 token permission layer 与 broker operation capability layer 的内部分离，但仍偏向“GitHub 权限映射 + 高风险操作补丁”。
- backend Phase 2 主要围绕 scoped token/grant 交付，尚未建立抽象 capability、resource selector、constraint 和 enforcement planner。
- `Administration` 仍可能在授权界面作为用户需要理解的权限出现。

## 3. 新行为/契约草案

### 3.1 用户层统一 capability 授权

Agent 审批模式和用户配置应呈现统一授权语义：

```text
哪个 agent
对哪些资源
能执行什么动作
在什么约束下
```

而不是：

```text
选择 GitHub permission
判断该权限由 token 还是 broker 实现
```

示例能力意图：

- 读取仓库内容；
- 写入指定分支；
- 删除符合 `agent/*` 且未受保护的短期分支；
- 创建 Pull Request；
- merge 满足条件的 Pull Request；
- 创建最多一个私有仓库；
- 对新建仓库应用安全 main protection；
- 禁止删除仓库、解除保护、任意修改设置或管理协作者。

具体 capability 名称、分组和 API schema 尚未冻结。

### 3.2 Per-agent 策略上限与 application 决缩减权

1. 每个 agent 必须有独立策略上限，不能使用全局公共仓库管理配置代替。
2. permission application/approval 只能在 agent 策略上限内缩小，不得扩大。
3. 同一 application 内不同仓库、不同 branch/ref、不同 resource selector 可有不同最终决定。
4. 高风险能力默认关闭或固定禁止；只有用户显式允许并满足约束时才可启用。
5. 审批界面必须按 agent 和 resource 呈现用户可理解的能力，而不是内部实现机制。

### 3.3 Resource selector 与 constraint

授权对象不能只停留在仓库级。契约应考虑以下 selector/constraint 维度：

- owner/repository；
- branch/ref pattern；
- default/protected branch 排除；
- path pattern；
- PR/issue 对象类型；
- repository creation owner、可见性、数量、命名约束；
- 次数、频率、有效期、TTL；
- 是否必须 merged/checks passed；
- 是否必须走 PR；
- 是否必须使用批准模板。

这些维度是否需要全部进入第一版尚未冻结。

### 3.4 实现无关的 enforcement planner

系统内部应将用户层 capability 编译为可验证的 enforcement plan。用户不需要看到该过程，但后端必须显式处理。

可能的 enforcement substrate：

1. **scoped token enforceable**：GitHub scoped token 权限粒度足够，且 agent 持有的 token 不能绕过用户约束。
2. **GitHub ruleset/protection assisted**：GitHub rulesets、branch protection 或 org/repo 设置能在 GitHub 侧硬阻断越权行为。
3. **broker-executed operation**：agent 不获得高权限 token，只请求 broker 执行受约束 operation。
4. **broker-mediated transport/proxy**：需要 broker 深度中介 Git/API 写操作，例如按 branch/path 限制 push；该能力复杂度和阶段边界未冻结。
5. **unavailable/fail closed**：当前没有安全实现方式时必须拒绝，不得用更宽 token 代替。

### 3.5 No-bypass invariant

核心安全不变量：

> 如果 broker 授予 agent 某项受限 capability，则 agent 不得同时持有能绕过该 capability 限制的 token、credential 或操作入口。

示例：

- 如果只允许删除 `agent/*` 短期分支，就不能同时向 agent 交付可删除任意普通分支的通用 `contents:write` token。
- 如果只允许通过 PR 修改 main，就不能向 agent 交付可直接 push main 的 token。
- 如果只允许创建仓库和模板化保护 main，就不能向 agent 交付 `administration:write` token。

若无法同时满足“授予该能力”和“防止绕过”，系统必须 fail closed，并在高级模式/审计中给出机器可读原因。

### 3.6 Administration 权限的用户层消解

1. `Administration` 不应作为 Agent 审批模式中的原始授权项。
2. 用户看到的应是具体管理能力和约束，例如创建仓库、模板化保护 main、删除受限短期分支。
3. 底层是否需要 administration-capable token 属于内部实现细节；该 token 不得离开 broker/daemon 边界。
4. `contents`、`pull_requests`、`issues` 等 GitHub permission 也可作为内部映射存在，但用户层应逐步转向能力语义，而不是 GitHub 权限名词堆砌。

### 3.7 审计与可见性分层

1. 用户层审计应记录 capability intent、resource、constraints、decision、result。
2. 高级/机器审计可记录 enforcement plan、内部 operation id、token permission mapping、ruleset dependency 和错误码。
3. Agent 审批模式不得暴露内部 operation id、executor、模板字段或“broker 代执行”等实现术语。
4. 审计不得记录 token、credential、client secret 或完整秘密派生值。

### 3.8 失败语义

1. 未知 capability、未知 resource selector、不可验证 constraint 或不安全 enforcement plan 必须 fail closed。
2. 不得因为用户“大概想允许”而自动扩大 token 权限。
3. 若 enforcement substrate 状态不可验证，例如 ruleset 不存在或权限不足，应拒绝并写审计。
4. 高风险操作部分失败时必须有明确补偿/审计策略；不得静默留下半完成状态。

## 4. 明确不包含

- 不批准 backend 恢复实现。
- 不批准最终 capability 名称、API schema、DSL 或 policy language。
- 不批准实现 broker-mediated git smart HTTP proxy。
- 不承诺第一版支持 branch/path 级任意写限制。
- 不批准自动配置 GitHub rulesets 或 branch protection。
- 不批准 raw token 兼容模式。
- 不表示真实 GitHub 权限、ruleset 或 token 行为已实测。

## 5. 迁移与回滚

当前已实现的 scoped/grant 基础仍有价值，可继续作为 token-enforceable capabilities 的底层交付机制；但在 CR-0003 冻结前不得继续按粗粒度 GitHub permission 契约扩展 exec/helper/policy。

CR-0002 暂时保留以记录演进上下文。CR-0003 定稿并获批准后，必须显式处理 CR-0002：归档、标记 superseded 或移动到约定归档位置；不得让多个过期授权契约长期并存。

## 6. 需要冻结前回答的语义清单

| 契约点 | 待冻结问题 |
|---|---|
| capability vocabulary | 用户层 capability 名称、分组和最小集合是什么 |
| resource selector | 第一版支持 repo/branch/path/owner 哪些维度和 pattern 语法 |
| per-agent policy | agent 持久策略上限与 application approval 的合并规则 |
| no-bypass enforcement | 每类 capability 如何判断 token/ruleset/broker/proxy 是否可满足 no-bypass |
| branch deletion | 是否以 broker-executed operation、ruleset-assisted，还是两者组合实现 |
| write mediation | branch/path 级写入限制是否进入后续阶段，以及是否需要 git/API proxy |
| Administration replacement | 哪些管理能力进入第一版，哪些固定禁止 |
| enforcement planner | policy/schema/API 如何表示 enforcement plan 和不可实现原因 |
| audit shape | 用户层 capability audit 与内部 enforcement audit 如何关联 |
| UX grouping | Agent 审批模式如何按 agent/resource/capability 分组而不增加心智负担 |
| ruleset dependency | GitHub plan/org/repo 权限差异如何处理 |
| phase boundary | scoped token、broker operation、ruleset assistant、proxy 分别属于哪个阶段 |

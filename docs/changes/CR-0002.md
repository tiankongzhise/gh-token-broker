# CR-0002 授权粒度与 broker operation capability 契约

- 日期：2026-11-28
- 状态：`proposed`
- 来源证据：2026-11-28 用户在高保真审核中指出：同一 application 内每个仓库必须能单独设置授权粒度；仅能在申请权限组内做细粒度降级；并进一步提出“允许 agent 创建仓库和设置 main 保护，但禁止删除操作”的粒度需求。用户随后批准采用 contract workspace 机制；后续审核又明确指出，审批模式不应暴露能力底层由 GitHub 原生权限还是 broker 代执行实现，用户心智应统一为“授权 agent 能做什么”。
- 影响范围：PRD、ARCHITECTURE、THREAT_MODEL、TEST_PLAN、DEVELOPMENT、WebUI 高保真、backend policy/schema/API、audit、后续 MCP/operation executor。
- 当前性质：**契约草案工作区，不是冻结契约，不是后端恢复实现授权。**
- 后续关系：CR-0003 已建立为更新的 capability-based authorization 范式草案；CR-0002 暂时保留为中间上下文，CR-0003 定稿后必须显式归档或标记 superseded。

## 1. 原因

高保真审核暴露出两个跨领域问题：

1. 低保真阶段“按仓库 + profile 降权，但不开放原子权限编辑”的粒度不足。用户需要在申请权限组上限内，对每个仓库分别选择 GitHub 原子权限的 `write/read/none`。
2. GitHub 原生权限不能把 `administration:write` 拆成“允许创建仓库/设置 branch protection，但禁止删除仓库/删除或弱化 protection”。如果这些操作直接交给 agent token 执行，权限必然过宽。

这不是单纯前端文案调整，而是授权模型、后端 schema、policy engine、审计、安全边界和交付通道契约的共同变化。

## 2. 原行为/原设计

- 审批以仓库 + permission profile 降权为主，不开放 GitHub 原子权限逐项编辑。
- 同一申请内多个仓库的最终粒度容易被设计成一个共用 profile。
- 高风险管理能力默认只是“是否授予 administration”。
- 后端主要围绕 scoped token/grant 交付设计，尚未明确 broker-side operation capability 层。

## 3. 新行为/契约草案

### 3.1 Per-repository permission matrix

1. 一个 permission application 可包含多个仓库。
2. 每个仓库必须有独立决定：`reject`、`approve_as_requested`、`approve_custom_subset`。
3. 每个仓库必须有独立权限矩阵；禁止多个仓库隐式共用同一组最终结果。
4. 申请 profile 是该仓库的权限上限，不是必须全量授予的结果。
5. 用户可在上限内对 GitHub 原子权限选择 `write/read/none`；不得超过该仓库申请上限。
6. 不在申请权限组内的权限必须不可选择。
7. UI 中的 `none` 表示不授予；调用 GitHub scoped token API 时应省略该 permission key，而不是发送 `none` 字符串。
8. 最终决定必须按仓库写审计。

### 3.2 统一用户授权心智

1. Agent 审批模式对用户呈现一套统一授权语义：用户决定“agent 能做什么”。
2. 用户不应被要求理解或区分某项能力底层由 GitHub scoped token permission、broker-side operation executor，或未来其他安全执行机制实现。
3. 高风险管理操作在审批模式中也必须以用户可理解的授权项表达，例如“创建仓库（受限）”“为新仓库保护 main（受限）”，并使用人类可读约束，例如“最多 1 个私有仓库”“只允许作用于本次创建的仓库”“必须使用安全保护模板”。
4. 内部 operation id、broker 代执行细节、模板字段和实现术语不得出现在 Agent 审批模式主流程；它们只属于人工/高级模式、后端契约、开发文档或机器审计详情。
5. 不能安全开放的删除、解除保护、任意设置修改、协作者管理等能力应对用户显示为不开放/固定禁止，而不是通过实现术语解释为什么做不到。

### 3.3 Token permission layer 与 operation capability layer 的内部分离

内部实现模型分为两层；该分层不得直接泄漏为 Agent 审批模式的用户心智负担：

1. **token permission layer**：用于普通数据面操作，例如 `contents`、`pull_requests`、`issues`、`actions`、`metadata` 等 GitHub 原生权限。它们可按仓库和 `write/read/none` 缩小，并通过 scoped token 交付。
2. **broker operation capability layer**：用于 GitHub 原生权限拆不细或风险过高的操作，例如创建仓库、设置 approved branch protection template、修改仓库设置、协作者管理等。这些操作不通过向 agent 交付高权限 token 实现，而由 broker 代执行。

### 3.4 Administration 安全边界

1. `administration:write` 包含创建仓库、删除仓库、仓库设置、团队/协作者和部分 Actions 配置等高风险能力。
2. 设置 branch protection 与删除/弱化 branch protection 都落在 `administration:write` 相关 endpoint 范围内；不能把该 token 交给 agent 后指望它只做保护不做删除。
3. 默认不得向 agent 交付带有 `administration:write` 的 scoped token。
4. 若用户批准“创建仓库 + 设置 main protection”能力，正确表达应是 broker operation capability，例如：
   - `create_repository_with_secure_baseline`
   - `configure_main_branch_protection`
5. broker 内部可以使用高权限 token 调 GitHub，但该 token 不得离开 daemon/broker 边界。

### 3.5 Secure branch protection template

broker 不应向 agent 开放任意 branch protection 参数。初版契约应使用批准模板，至少包含：

- `enforce_admins: true`
- `allow_force_pushes: false`
- `allow_deletions: false`
- `required_linear_history: true`（是否默认启用待最终契约确认）
- required status checks：strict，上下文由项目/用户配置
- PR review 要求：是否默认需要，待最终契约确认

agent 只能选择应用模板，不能把保护弱化。

### 3.6 权限交集边界

GitHub App user access token 的有效能力是以下边界交集：

- 用户本人对仓库/组织的权限；
- GitHub App 安装/授权获得的权限；
- scoped token 进一步缩小的权限；
- scoped token repository selection；
- endpoint 自身要求和额外权限组合。

broker 不得把 scoped token 描述为能放大用户或 App 原没有能力。

### 3.7 审计与错误语义

1. 审计必须按仓库记录最终 permission matrix。
2. operation capability 的创建、允许、拒绝、执行成功/失败必须单独审计。
3. 审计不得记录 token、credential、client secret 或完整秘密派生值。
4. policy denied 必须区分：仓库不匹配、权限超过上限、operation capability 不允许、模板参数不允许、min_ttl 不满足。
5. 高风险操作失败必须失败关闭，不得回退到更宽 token 或 raw token。

## 4. 明确不包含

- 不批准后端恢复实现。
- 不批准自动创建仓库或自动修改 branch protection。
- 不批准 MCP/operation executor 的最终 API schema。
- 不批准 raw token 兼容模式。
- 不表示真实 GitHub 权限行为已实测；仍需测试矩阵。

## 5. 迁移与回滚

当前后端只有 scoped/grant 基础，尚未接通 exec/helper 或 operation executor。若本契约被修改或否决，应停止基于该契约的后端实现；已实现的 grant/inventory 基础可保留，不依赖 administration token 交付路径。

## 6. 需要高保真审核后冻结的语义清单

| 契约点 | 待冻结问题 |
|---|---|
| per-repository matrix | 是否按当前高保真三仓示例确认 |
| profile ceiling | profile 是否始终作为硬上限 |
| write/read/none | 是否所有仓库权限都用三态，是否存在只有 read/write 的权限 |
| none encoding | 是否统一在 scoped token 请求中省略 key |
| 用户授权心智 | Agent 审批模式是否完全隐藏实现机制，只展示统一授权项 |
| operation capability | 第一版允许哪些内部 operation id |
| secure repo creation | 是否进入 Phase 2/3，还是后续阶段 |
| branch protection template | required checks/review/linear history 默认值 |
| audit shape | 每仓库决定与 operation 事件的字段 |
| error taxonomy | policy denied/operation denied 的机器可读错误码 |
